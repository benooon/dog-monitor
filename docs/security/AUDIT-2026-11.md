# Security audit, November 2026 (backend + iOS credential storage)

## Run
- **Profile:** quick (one hunter wave, one final coverage critic, one independent verifier per candidate). This is a partial pass, not complete coverage.
- **Scope:** `backend/`, the DogMonitorCore API client and session storage (`ios/Packages/DogMonitorCore/Sources/DogMonitorCore/API`, `Session/`), `ios/App/KeychainStore.swift`. CI, Railway config, the rest of the iOS app, `scripts/` and `marketing/` were out of scope.
- **Source ref:** `cd2dc61` (clean). Method: vendored `security-audit` skill (`.claude/skills/security-audit`).
- **Budget:** 16 agent invocations planned, 13 spent (5 hunters, 1 critic, 7 verifiers). Reconnaissance was done by the coordinating agent directly instead of four recon agents.
- **Execution:** sandboxed source-and-local-only. Local checks ran vitest files against a disposable copy of `backend/` inside an OS-enforced sandbox: new network/mount/pid namespaces with loopback only, a read-only filesystem except scratch, an empty allowlisted environment, an unprivileged uid, rlimits and a timeout, and a private Postgres. No deployed endpoint, LiveKit, Apple or Railway service was contacted. Swift was reviewed from source only.
- **Prior runs:** none. This is the first ledger for the repository.
- **Fix status:** all four confirmed findings were fixed in `d7d94fd` with regression tests (see each finding). The needs-validation leads stay open (`docs/BACKLOG.md`, `docs/HUMAN_TODO.md`).

## Posture
Identity and tenancy are solid. Apple sign-in, the session JWT, device secrets, and the household scoping on every viewer and camera route held up under review, and so did media keys and presigned URLs. The confirmed problems are at the edges: a token that was broader than intended, a rate limiter that could be raced, entitlement state that forgot a refund, and realtime sockets that outlived access. None of them let an outsider read another household's data without first getting a secret (an export key or an active invite code).

### Refunded App Store subscription can be restored by replaying the pre-refund signed transaction (medium)

`backend/src/billing/apply-transaction.ts:revocation-not-persisted-replay`

When Apple refunds or revokes a subscription, applyTransaction sets the household to free and clears planExpiresAt, but keeps no record that the transaction was revoked. POST /subscription/apple accepts any validly signed transaction, however old. A household owner who kept the signed transaction their app posted at purchase can post it again after the refund. Premium then comes back until that transaction's original expiresDate: up to a year for the yearly product, up to a month for the monthly one.

**Root cause.** The revocation branch of applyTransaction (apply-transaction.ts:12-17) only writes plan=free and planExpiresAt=null and stores neither the revocation nor its time. In the non-revoked branch, extendsPremium = !current?.expiresAt || ... (line 26) is true once planExpiresAt is null, so the guard on line 27 does not stop an older transaction from the same subscription. The verifier (app-store.ts verify/parsePayload) checks only chain, signature, bundle and product. It never reads purchaseDate or signedDate, and nothing checks revocation state, so an earlier Apple-signed JWS without revocationDate is accepted again and written as premium (lines 28-37).

**Lower-trust principal.** A household owner who bought Premium, kept the StoreKit signed transaction, and then got a refund from Apple

**Source path**
1. entrypoint `backend/src/routes/subscription.ts:47` (POST /subscription/apple (requireOwner)): A signed-in household owner submits signedTransaction, which can be any Apple-signed JWS, however old
2. propagation `backend/src/routes/subscription.ts:66` (verifier.verify): Checks the x5c chain, the signature, the bundle and the product. Nothing checks signedDate, purchaseDate or revocation state. The appAccountToken check (line 71) and the cross-household check (lines 75-86) both pass for the owner's own household.
3. propagation `backend/src/billing/apply-transaction.ts:12` (applyTransaction revocation branch): An earlier REFUND notification (POST /app-store/notifications, subscription.ts:160) set plan=free and planExpiresAt=null and stored nothing about the revocation
4. sink `backend/src/billing/apply-transaction.ts:28` (applyTransaction premium update): Because current.expiresAt is null, extendsPremium is true (line 26), so the replayed transaction writes plan=premium and planExpiresAt = its original expiresDate

**Conditions**
- authentication_level: Signed-in household owner (requireOwner on POST /subscription/apple)
- data_state: The owner kept a copy of the signed transaction JWS their app posted at purchase, for example by capturing their own app's HTTPS traffic through a user-installed CA. Apple then refunded or revoked it, and the REFUND/REVOKE notification was applied.
- timing_dependency: The replay must happen before the transaction's original expiresDate, and while the JWS's x5c certificates are still within their validity window (verifyPayload checks the validity window against the current time)
- system_configuration: Only matters when ENFORCE_PLAN_LIMITS is on. When it is off, every household gets the full camera limit anyway (plans.ts cameraLimit).

**Bounded reproduction (local sandbox).** Add test/v3-refund-replay.test.ts (in the evidence file) to a copy of backend/ and run it with /srv/security-audit/tools/run-backend-check.sh. It uses a private Postgres and the repo's test App Store chain fixtures, and backend/src is unmodified. T0: sign in, create a household, and POST /subscription/apple a signed transaction (appAccountToken = household id, expiresDate = T0+365d or T0+30d). Keep the JWS. T0+10d: POST /app-store/notifications with a REFUND notification whose signedTransactionInfo is the same transaction plus revocationDate. GET /subscription now shows free. T0+20d: POST /subscription/apple again with the saved pre-refund JWS, then GET /subscription.

**Observed.** Yearly: purchase gave 200 premium until 2028-02-29. After the REFUND, plan was free with expiresAt null and cameras limit 1. The replay returned 200 premium until 2028-02-29 with cameras limit 4, and GET /subscription still showed premium. Monthly behaved the same: the replay restored premium until 2027-03-31.

**Priority.** Likelihood medium: Needs a paying owner who deliberately captures their own app's signed transaction (with a user-installed CA or similar), then asks Apple for a refund and reposts the JWS. No special access is needed, but it is a deliberate fraud by an authenticated customer, not something an outsider can do. Impact medium: A paid entitlement (the Premium camera limit, 4 instead of 1) is used without payment until the original transaction's expiresDate: at most one billing period per refunded purchase. No other household's data or identity is affected.

**Fix.** Persist the revocation and refuse to grant premium again from any transaction of the same subscription bought at or before it. Add a nullable households.planRevokedAt (or a revoked_transactions table keyed by originalTransactionId) with a migration. Set it in the revocation branch and keep planOriginalTransactionId. Parse purchaseDate in parsePayload and require it. In applyTransaction, when originalTransactionId matches the household's subscription and a revocation is recorded, ignore transactions whose purchaseDate is at or before planRevokedAt. Clear planRevokedAt when a genuinely newer transaction grants premium. Optionally confirm state with the App Store Server API (Get Transaction Info / Get All Subscription Statuses) before granting from a client-posted transaction. Regression test: purchase, REFUND, replay the original JWS, expect the plan to stay free; a new renewal with a later purchaseDate still grants premium. Shipped in `d7d94fd`.

### Invite-code brute-force limiter is check-then-record, so concurrent guesses bypass it (medium)

`backend/src/routes/invites.ts:invite-accept-limiter-check-then-record-race`

POST /invites/:token/accept checks limiter.isBlocked(request.ip) at the start of the handler and calls limiter.recordFailure only after the database transaction has evaluated the guess and thrown a 404 AcceptError. Every request that is in flight at the same time passes the check before any failure is recorded, so one client address can evaluate far more than the intended 10 six-digit code guesses per 10-minute window by sending them concurrently. With the production-default limiter, a 101-request concurrent burst from one address had all 100 wrong codes evaluated (404, none 429) and the real code in the same burst redeemed as a camera (201 with a deviceSecret for the victim household). A correct guess of an active code gives an unauthenticated client a camera identity in the victim household, or gives any signed-in user who is not yet in a household membership with live view, timeline and media access.

**Root cause.** AttemptLimiter exposes separate isBlocked() and recordFailure() calls (backend/src/pairing/attempt-limiter.ts:14 and :18), and invites.ts calls them on either side of await points (backend/src/routes/invites.ts:87 before the auth/DB awaits, :162 after the transaction rejects). The limit therefore counts completed failures instead of reserving an attempt before the code is looked up.

**Lower-trust principal.** Unauthenticated client at a single address sending many concurrent POST /invites/<6-digit code>/accept requests with {"as":"camera"}

**Source path**
1. entrypoint `backend/src/routes/invites.ts:59` (POST /invites/:token/accept): Public route: no auth for as=camera, any valid user JWT for as=member; the :token param may be a 6-digit code
2. propagation `backend/src/routes/invites.ts:87` (limiter.isBlocked(limiterKey)): Synchronous read of failures recorded so far; requests already in flight all see the same pre-burst count and continue
3. propagation `backend/src/routes/invites.ts:110` (db.transaction: UPDATE invites SET used_at WHERE code = param AND unused AND unexpired RETURNING): Each in-flight request evaluates its guess against all active invites (code param selected at line 103/115)
4. sink `backend/src/routes/invites.ts:162` (limiter.recordFailure(limiterKey) on 404): Failure is recorded only after the guess was evaluated; a hit instead returns 201 with deviceSecret (line 157) or 200 household membership (line 133)

**Conditions**
- authentication_level: None for camera redemption; for member redemption any Sign in with Apple account not already in a household
- data_state: At least one unused, unexpired invite code exists (10-minute TTL); each evaluated wrong guess hits with probability about (active codes)/10^6
- timing_dependency: Guesses must be in flight concurrently; the number evaluated per window is bounded by connection and server concurrency, not by the limiter

**Bounded reproduction (local sandbox).** In the sandbox, build the app with buildTestApp(h) and no inviteLimiter override, so the production default AttemptLimiter(10, 600000) is used Sign in a victim owner, create a household, and POST /invites to get an active 6-digit code Send the 101 accepts at once with Promise.all(app.inject(...)) from the same client address (no X-Forwarded-For) Count status codes, check the real-code response for deviceSecret and householdId, then send one more bad guess

**Observed.** V5_BURST {"burst":101,"statusCounts":{"201":1,"404":100},"realCodeStatus":201,"realCodeHousehold":true,"deviceSecretReturned":true,"afterBurstStatus":429} - 100 wrong guesses were evaluated under a 10-failure limit and the real code redeemed as a camera in the victim household; only the request after the burst was blocked.

**Priority.** Likelihood low: Needs an active invite inside its 10-minute window and sustained large concurrent bursts; each evaluated guess has roughly (active codes)/10^6 chance, so a hit needs on the order of hundreds of thousands of requests per active code, which the limiter no longer caps but connection/server capacity still does Impact high: Demonstrated: a hit returns a camera device secret in the victim household (can post events, media and pushes, join realtime). By the same code path, as=member grants membership with live video, timeline and media

**Fix.** Count the attempt atomically before evaluating the guess: replace isBlocked/recordFailure with a synchronous tryAcquire that checks and records in one step (no await between them), call it before authentication and the DB transaction for code-shaped params, and drop the later recordFailure. Because the limiter is per-process and per-address, also add a global cap on failed code redemptions across all clients (or persist attempts in Postgres) so throughput cannot be scaled by instances or addresses. The X-Forwarded-For keying issue noted by the hunter is a separate root cause and is not fixed by this change. Shipped in `d7d94fd`.

### Training export key is a full owner session token that can add members and renew itself (medium)

`backend/src/routes/training.ts:export-token-unscoped-session-jwt`

POST /training/export-token is meant to give out a one-hour key that only reads labeled training clips, 'so the app's long-lived session never leaves the phone'. The app puts the key on the general pasteboard (UIPasteboard.general), and docs/TRAINING.md tells the owner to paste it into DOGMONITOR_TOKEN on a Mac for scripts/export-training-data.mjs. But the key comes from the same JwtService.issue call as the 30-day session, with only a shorter TTL. It has the same sub, iss and aud and no scope claim, so app.authenticate cannot tell it apart from a session. Anyone who gets the key within its hour (pasteboard or Universal Clipboard, shell history or environment, the machine running the script) has the owner's full API rights. They can create an invite and join the household as a member with their own Apple account, which keeps live view, timeline and media access after the key expires. They can also change household state (shown here: rename) and mint new export keys with the export key, as long as training sharing stays on.

**Root cause.** JwtService.issue(claims, ttlSeconds) (backend/src/auth/jwt.ts:22) takes no audience or scope, so the export token (training.ts:34) and the session token (auth.ts:64) differ only in exp. JwtService.verify (jwt.ts:34) checks only iss, aud and HS256, and the authPlugin (plugin.ts:22) accepts any verified token on every route. That includes POST /training/export-token, so an export key can mint another one.

**Lower-trust principal.** Someone who holds only the owner's one-hour training export key

**Source path**
1. entrypoint `backend/src/routes/training.ts:32` (POST /training/export-token): An owner session (or an existing export key) asks for a one-hour export key
2. propagation `backend/src/routes/training.ts:34` (POST /training/export-token): opts.jwt.issue({ userId }, EXPORT_TOKEN_TTL_SECONDS): only the TTL changes, no scope or audience
3. propagation `backend/src/auth/jwt.ts:22` (JwtService.issue): Signs an empty payload with the same sub, iss 'dog-monitor' and aud 'dog-monitor-app' as the session token
4. propagation `ios/App/Household/HouseholdView.swift:201` (HouseholdView training section): The key goes on UIPasteboard.general. docs/TRAINING.md says to paste it into DOGMONITOR_TOKEN on a Mac
5. propagation `backend/src/auth/plugin.ts:22` (app.authenticate): Any token that passes JwtService.verify becomes request.user, with no scope check
6. sink `backend/src/routes/invites.ts:36` (POST /invites): authenticate + requireHousehold + requireOwner accept the export key. The invite it creates lets an outsider join as a persistent member

**Conditions**
- data_state: The household owner has turned on training data sharing (shareTrainingData) and generated an export key
- user_interaction: The attacker gets the export key within its one-hour lifetime, for example from the general pasteboard or Universal Clipboard, shell history or environment, or a compromised machine running the export script
- authentication_level: The attacker needs only the export key, plus any Apple account to accept the invite and keep access

**Bounded reproduction (local sandbox).** Run test/v7-export-token.test.ts against a disposable copy of backend/ with a private loopback Postgres (run-backend-check.sh sandbox, no external network) Sign in as the owner, POST /households, PATCH /household {shareTrainingData:true}, POST /training/export-token, and decode the session and export JWTs With only the export token: GET /me, POST /invites, PATCH /household (rename), POST /training/export-token Sign in as a second user, accept the invite as a member, then GET /household

**Observed.** Both JWTs have the claim set aud,exp,iat,iss,sub with aud=dog-monitor-app, iss=dog-monitor and the same sub. With the export token: GET /me 200 (role owner), POST /invites 201, PATCH /household 200 (name changed), POST /training/export-token 200. The outsider's accept returned 200 {role: member}, and their GET /household returned 200 with the renamed household and 2 members.

**Priority.** Likelihood low: The key has to leak within one hour, and only after the owner opts in and generates one. But the intended flow puts it on the general pasteboard and in a shell env var off the phone. Impact high: The holder gets the owner's API rights over the household. The repro shows a one-hour key turned into a lasting household membership (live view, timeline and clips through the member role), a change to household state, and a self-renewing export key.

**Fix.** Give export keys their own audience (or a scope claim). app.authenticate verifies the session audience only. Only GET /training/labeled accepts the export audience, and it still applies requireHousehold, requireOwner and the opt-in check. POST /training/export-token requires a real session, so an export key cannot mint another one. Add regression tests that an export key gets 401 on GET /me, POST /invites, PATCH /household and POST /training/export-token. Shipped in `d7d94fd`.

### Realtime WebSocket keeps household access after member removal or camera revocation (low)

`backend/src/routes/realtime.ts:ws-authorization-only-at-upgrade`

GET /ws checks the viewer's household and the camera's identity once, at upgrade, and never again. A removed member's open socket keeps getting the former household's camera presence and dog state (for example barking), and its watch messages still reach the camera as viewer joins. A revoked camera's open socket keeps writing heartbeats, battery and dog state to its revoked device row and pushing cameraState to the household's viewers and to the state/presence listeners (live activities). Server pings every 30 s keep these sockets alive, so access lasts until the client disconnects.

**Root cause.** setUpViewer (backend/src/routes/realtime.ts) resolves householdId from findMembership once at connect and reuses it for watch checks and for hub.toHousehold broadcasts. setUpCamera trusts request.device from the upgrade, and its heartbeat UPDATE is keyed only by deviceId, with no status = 'active' filter. DELETE /household/members/:userId and POST /devices/:id/revoke only update the database. RealtimeHub keeps no socket references and has no way to drop a user's or device's peers, and nothing else calls into the hub on removal or revocation.

**Lower-trust principal.** A household member the owner then removed, or a camera (for example a lost or handed-off phone) the owner then revoked, each holding an already-open /ws socket

**Source path**
1. entrypoint `backend/src/routes/realtime.ts:40` (GET /ws upgrade): The Bearer JWT or Device credential is checked once in preValidation (authenticateEither). The device check needs status active only at this point.
2. propagation `backend/src/routes/realtime.ts:99` (setUpViewer): householdId comes from findMembership at connect and is captured for the life of the socket. It is registered in the hub through viewerConnected.
3. propagation `backend/src/routes/households.ts:114` (DELETE /household/members/:userId): Deletes the membership row and revokes the member's devices inside a DB transaction. Nothing touches the hub or open sockets.
4. propagation `backend/src/routes/devices.ts:159` (POST /devices/:id/revoke): Sets status revoked and clears the secret hash in the DB only. The camera's open socket is untouched.
5. propagation `backend/src/routes/realtime.ts:82` (setUpCamera onMessage): A revoked camera's heartbeat still goes to hub.heartbeat and to an UPDATE of its device row
6. propagation `backend/src/realtime/hub.ts:193` (RealtimeHub.toHousehold): presence and cameraState go to every viewer peer whose stored householdId matches, including the removed member's peer
7. sink `backend/src/realtime/hub.ts:143` (RealtimeHub.watch): The removed member's watch is added to the watchers and the camera gets a viewers joined message

**Conditions**
- authentication_level: The principal had a valid session (member JWT or camera device secret) and opened /ws before the removal or revocation
- timing_dependency: The socket stays open across the owner's removal or revocation. Server pings every 30 s keep it alive, so access lasts until the client disconnects.

**Bounded reproduction (local sandbox).** Run test/v6-ws-revocation.test.ts with /srv/security-audit/tools/run-backend-check.sh (sandboxed backend copy, app.injectWS, private loopback Postgres, no external network) Case 1: the owner creates a household and pairs a camera, and a member joins with an invite. The camera and the member connect to /ws. The owner calls DELETE /household/members/<member>, and the member's GET /household now returns 403. The camera sends a heartbeat with state barking, then the removed member sends watch for the camera. Case 2: the owner's viewer and the camera connect to /ws. The owner calls POST /devices/<camera>/revoke, and the old secret now gets 401 on GET /device/me. The camera sends a heartbeat with battery 0.07 and state barking over the open socket. Read the device row.

**Observed.** Case 1: the removed member's socket received {type:presence, online:true} and {type:cameraState, state:barking} for the former household's camera. After its watch, the camera received {type:viewers, count:1, change:joined}, and hub.isWatching(camera, removedMember) was true. Case 2: the owner's viewer received presence online:true and cameraState barking from the revoked camera. The device row read {battery:0.07, status:revoked, dogState:barking}.

**Priority.** Likelihood medium: Needs a socket that is already open when the owner acts. Cameras hold /ws continuously and viewers hold it while in the foreground, so a revoked camera or a removed member who is still connected is a realistic case. No privilege beyond the prior legitimate session is needed. Impact low: Ongoing disclosure of camera presence and dog-state metadata to a removed member, viewer-join signals to the camera, and injection of false dog state, battery and presence into a household by a revoked device (shown to viewers, stored in the device row, sent to live activities). No video, media or timeline access was shown. The live-token HTTP route re-checks membership and device status.

**Fix.** Bind realtime sessions to current authorization. (1) Keep the socket (or a close callback) in each hub peer, along with the userId and deviceId. Add RealtimeHub.disconnectUser(userId) and disconnectDevice(deviceId), which close those peers with 4003 and remove them from viewers, watchers and camera peers. Call them after the DB commit in DELETE /household/members/:userId (for the user and each revoked device), POST /devices/:id/revoke, and household deletion. (2) Defense in depth for multi-instance deployments: add eq(devices.status, 'active') to the camera heartbeat UPDATE and close the socket when no row is updated. Re-run findMembership before each viewer watch and close if the household changed. Optionally re-validate periodically on the ping timer, so broadcasts to an idle removed viewer also stop. Regression tests: both cases above should end with the socket closed with code 4003 and no further household messages. Shipped in `d7d94fd`.

## Hardening notes (not findings)

- backend/src/routes/landing.ts:89 publicOrigin uses request.host, which trustProxy: true takes from X-Forwarded-Host. The value is regex-limited to hostname characters, HTML-escaped, and the page is served with cache-control: no-cache, so it only spoofs OG/canonical URLs in the attacker's own response. A configured PUBLIC_ORIGIN would remove this.
- ios/App/Household/HouseholdView.swift:201 copies the 1-hour export JWT to UIPasteboard.general without an expiry. setItems with an .expirationDate matching the token TTL would limit how long it stays on the clipboard and in Universal Clipboard.
- backend/src/pairing/attempt-limiter.ts is per-process memory: limits reset on every deploy or restart and are not shared across replicas.
- Camera and member limit checks in invites.ts (count then insert) and POST /devices run under READ COMMITTED without a lock, so concurrent redemptions of several owner-issued invites can exceed LIMITS/plan camera limits; owner-controlled, low impact. A row lock on the household or a unique-constrained counter would close it.
- AttemptLimiter is in-memory per process; scaling Railway to more than one instance multiplies the guess budget and restarts reset it. Move it to Postgres or a shared store if replicas are added.
- Camera redemption by 6-digit code needs no authentication at all; requiring the 192-bit token for camera pairing (QR) and keeping codes only for signed-in members would remove the unauthenticated guessing surface.
- backend/src/routes/dogs.ts: create/patch/delete dog and photo upload/delete have no requireOwner, so any household member can edit or delete the household's dog profiles. SPEC/DECISIONS do not state dogs are owner-only (only revoke, invites, household settings and billing are), so this is a policy choice to confirm rather than a finding.
- Presigned download URLs are bearer links not revocable on ACL change: 10 min for timeline/snapshot media and 6 h for the push snapshot URL (SNAPSHOT_URL_TTL_SECONDS). A member removed via DELETE /household/members/:userId keeps any URL already issued until it expires; retention purge also leaves links working until the object is deleted. Bounded by TTL; consider a shorter push TTL.
- backend/src/routes/live-activities.ts: the upsert on push_token conflict reassigns an existing row's householdId/userId/cameraId to the latest caller. That is only exploitable with another user's ActivityKit push token (not exposed by the API), but binding the conflict update to the same userId would close it.
- backend/src/routes/media.ts POST /device/uploads does not check that the eventId exists or belongs to the camera, and a revoked camera's already-issued PUT URLs stay valid for up to 15 min. Writes are limited to the camera's own prefix, but objects uploaded for events that never get a DB row are never removed by the DB-driven retention job (storage lifecycle gap, not cross-tenant).
- dogs.photoKey is a free-form string up to 500 chars that any member can set, with no prefix validation. Nothing presigns it today; if it is ever signed, bind it to a household prefix the way events.ts does for media keys.
- backend/src/routes/devices.ts POST /devices lets any member register a role=camera row with no secret. It cannot authenticate, but it uses up the household's camera limit slots until the owner revokes it.
- Session JWTs (30-day default) have no revocation or jti. Removing a member is enforced by requireHousehold's membership lookup, not by token invalidation, so a leaked session stays valid for /me and household creation until exp.
- The Apple sign-in nonce is generated by the client and not recorded as used on the server. A captured (identityToken, rawNonce) pair can be replayed within the Apple token's lifetime. Getting the pair requires the TLS request body, so this is not a finding.
- Viewer limit: POST /cameras/:id/live-token counts only /ws watchers (hub.viewerCount), so a member can mint LiveKit viewer tokens without registering a watch, and the viewers-per-camera limit is advisory. It is a same-household quota, not an isolation break.
- App Store notifications are not deduplicated by notificationUUID and signedDate is not checked. Out-of-order handling depends only on expiresAt comparisons in applyTransaction.
- The camera limit is enforced only at pairing (invites route), so any short Premium window (refund replay, sandbox transaction) leaves extra cameras paired after it lapses. This is documented behavior, but it amplifies both billing candidates.

## Positive patterns
- Every viewer route resolves the household from the caller's membership row on each request, never from input, and every query filters on it.
- Camera media keys are built on the server, and stored keys are checked against the camera's own prefix before anything is signed or deleted.
- Apple identity tokens and App Store JWS chains are verified with pinned algorithms, issuer, audience and root. Nothing falls back to unverified data.
- Credentials on the phone are a single Keychain item with `AfterFirstUnlockThisDeviceOnly`, sent only to the configured HTTPS API.
- The public landing and waitlist pages have a strict CSP, escaped templates, the same answer for new and existing emails, and no open redirects.
