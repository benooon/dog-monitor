# Decisions log

One line per decision: `YYYY-MM-DD — decision — why`.

- 2026-11-10 — Native Swift/SwiftUI rather than Expo — the camera + WebRTC + on-device ML pipeline needs direct AVCaptureSession control; iOS-only for now.
- 2026-11-10 — Build from scratch rather than forking Clearcam — Clearcam is GPL-3 Objective-C and its remote features depend on its closed clearcam.org backend; it may be read as reference only, with no code copied.
- 2026-11-10 — Backend on Railway (Node/TS/Fastify/Postgres) instead of Firebase — the owner already uses Railway.
- 2026-11-10 — LiveKit Cloud as SFU — multiple viewers per camera without overloading the camera phone.
- 2026-11-10 — XcodeGen, no committed .xcodeproj — agents work on Linux and must not hand-edit pbxproj files.
- 2026-11-10 — Agents push directly to main, with no PRs — the owner granted full autonomy; CI results are published to the `ci-results` branch.
- 2026-11-10 — CI decides whether to run the iOS job by diffing against the last commit the iOS job ran on (`ios-sha.txt` in ci-results), not the previous push — with cancel-in-progress, a quick docs push cancelled the iOS run and then reported the old result as carried over.
- 2026-11-10 — Core tests use XCTest (not Swift Testing) — works identically on the Linux container and Xcode; can switch later.
- 2026-11-10 — Backend deploys on Railway via `backend/Dockerfile` + `railway.json` (health check `/health`) rather than Nixpacks — reproducible builds, same image locally.
- 2026-11-10 — Backend dev tooling: ESLint 9 flat config + typescript-eslint, Vitest, tsx; `npm run lint` also runs `tsc --noEmit`.
- 2026-11-10 — DB: `pg` (node-postgres) driver with Drizzle; event types/dog states stored as text (mirroring DogMonitorCore raw values) instead of PG enums so new values need no enum migration; migrations run on Railway via `preDeployCommand` (`npm run migrate:prod`).
- 2026-11-10 — `devices.user_id` (nullable) added beyond SPEC §9 so viewer devices map to users for push fan-out; `notification_prefs.device_id` null means all cameras (unique NULLS NOT DISTINCT, needs PG 15+).
- 2026-11-10 — New backend deps: `jose` (Apple JWKS verification + our HS256 JWTs; zero-dep, standard) and `fastify-plugin` (official, to expose `app.authenticate`). Apple tokens are checked for issuer, audience (`APPLE_AUDIENCES`), RS256 and expiry; nonce checking deferred until the iOS flow sends one.
- 2026-11-10 — MVP: a user belongs to at most one household (`POST /households` returns 409 otherwise) so every route can be scoped without a household id in the path; revisit if multi-household is needed.
- 2026-11-10 — API never returns `device_secret_hash` or raw APNs tokens (only `hasPushToken`); only the owner revokes devices; a device is updated by its own user or the owner.
- 2026-11-10 — Pairing: one invite carries both a long token (QR/link) and a 6-digit code; `POST /invites/:token/accept` takes either, with body `{as: "member"}` (needs user JWT) or `{as: "camera", deviceName}` (no user; returns a one-time `deviceSecret`). Device auth header: `Authorization: Device <deviceId>:<secret>`, secret stored as SHA-256. Failed redemptions are rate-limited per IP in memory (10 per 10 min) against code brute-forcing.
- 2026-11-10 — Viewer onboarding state (`OnboardingState`) and credential persistence (`CredentialStore` over a `SecureStore` protocol) live in DogMonitorCore; the app supplies a Keychain-backed store (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`). API base URL comes from build setting `API_BASE_URL` via Info.plist `DMAPIBaseURL`.
- 2026-11-10 — CI no longer publishes RED for cancelled (superseded) runs and no longer cancels in-progress runs; the RED for bc6ec2a/237dbd8 was a cancellation, not a failure.
- 2026-11-10 — `POST /auth/apple` now requires `nonce` (raw); the token's `nonce` claim must equal its SHA-256 hex. The iOS app generates a fresh nonce per sign-in (CryptoKit) — prevents replaying a captured identity token.
- 2026-11-10 — Took the core event engine ahead of bark detection: bark detection consumes the capture pipeline's audio stream, which another agent is building right now.
- 2026-11-10 — Added livekit-server-sdk (backend) to mint LiveKit room tokens, as SPEC §6 prescribes. One room per camera (`camera-<deviceId>`); viewers may publish microphone only (push-to-talk); without LIVEKIT_* the live routes answer 503 instead of faking tokens.
- 2026-11-10 — Added @fastify/websocket (+ @types/ws) for the realtime channel `GET /ws` (protocol in backend/src/realtime/protocol.ts). Presence lives in memory in one API instance (Railway runs one replica); scaling out would need Redis or Postgres LISTEN/NOTIFY. A camera counts as online while its last heartbeat is under 3 min old, so a dropped socket alone does not flap presence.
- 2026-11-10 — Moved the pairing UI task into Phase 1: a camera needs device credentials before it can join the realtime channel or LiveKit. Camera publishing is video-only for now (mic is owned by AVCaptureSession for bark detection).
- 2026-11-10 — Event engine: per-type channels (barking = bark+growl, whining = whimper+howl, plus atDoor/forbiddenZone/notVisible fed by the visual classifier). An event fires when an episode lasts `minDuration` or reaches `countThreshold` hits in 60 s; a new qualifying episode within the 5-min cooldown after the last event ended *resumes* that event (no new push) unless "calmed down" was already sent; calmedDown fires once after 2 min of quiet following a barking/whining event.
- 2026-11-10 — The keychain holds one credential, so pairing a phone as a camera replaces a signed-in user on that phone (a phone is either a camera or a viewer). Pairing QR content is `dogmonitor://pair?t=<token>`.
- 2026-11-10 — Moved the storage service before the Notification Service Extension: the extension needs a snapshot URL. Pushes will carry a short-lived presigned snapshot URL so the extension needs no credentials.
- 2026-11-10 — Added @aws-sdk/client-s3 + s3-request-presigner for clip storage (presigned PUT/GET, batch delete) instead of hand-rolling SigV4. Media keys are `households/<h>/cameras/<c>/events/<e>/{clip.mp4,snapshot.jpg}` so ownership is checked from the key; retention deletes objects by DB lookup (no bucket listing).
- 2026-11-10 — Camera audio reaches LiveKit through manual rendering mode (`AudioManager.setManualRenderingMode(true)` + `mixer.capture(appAudio:)` fed from AVCaptureSession), so the capture session keeps sole ownership of the mic for bark detection. Trade-off: remote audio is not auto-played on the camera, which push-to-talk must handle (render remote tracks itself).
- 2026-11-10 — Quiet hours use the phone's time zone (devices.time_zone, sent at push registration) and hold back passive/active pushes only; time-sensitive alerts (prolonged barking, whining, camera offline, battery, heat) still come through, since they may mean the dog is in distress.
- 2026-11-10 — Event clips come from one continuously running AVAssetWriter in fragmented-MP4 (HLS profile) mode that hands ~1 s segments to memory; a pure `ClipAssembler` in core keeps 5 s of pre-roll and cuts 5 s + 10 s (20 s max) per event. Clips are init segment + segments concatenated (plays in AVPlayer). Recording runs only on paired cameras; local files are pruned after 2 days.
- 2026-11-10 — The camera uploads an event's snapshot before `POST /events` (waiting up to 2 s for the frame) so the first push carries it; this delays that push by about one upload. Clips (ready ~10 s later) and snapshots that failed inline go through a persisted media queue and are attached with `PATCH /events/:id`; 404 (event not created yet) is retried up to 30 times.
- 2026-11-10 — Notification settings save with Cancel/Save in a sheet; one quiet-hours window for all non-urgent types (copied onto each row, since the backend stores it per row); per-camera choices stored only while they differ from the household setting. Why: matches the backend model with no schema change and keeps the screen simple.
- 2026-11-10 — Camera power alerts use the existing `lowBattery` event type, reworded "The camera isn't charging": it fires after 2 min off the charger or at once below 20 % off the charger, and ends when charging resumes. Overheating fires after 30 s at serious+; capture drops to 15 fps (serious) / 10 fps (critical). Why: SPEC §6 asks to alert on unplug as well as low battery, without a new event type.
- 2026-11-10 — Push-to-talk is tap-to-talk (not hold), and the viewer's playback of camera audio pauses while talking to avoid hearing their own echo. On the camera, viewer audio is rendered from each RemoteAudioTrack into our own AVAudioEngine (LiveKit is in manual rendering mode there), and the capture session no longer configures the audio session itself: we set playAndRecord + defaultToSpeaker so the voice comes from the speaker.
- 2026-11-10 — Invite links are `https://<API host>/invite/<token>`: the backend serves the AASA file and a short browser fallback, so no separate website is needed. The link fills in the join screen rather than joining on its own (one tap to confirm). Removing a member revokes their phones and deletes their push settings.
- 2026-11-10 — Motion detection compares 64-px-wide luma frames at up to 4 fps (pixel change ≥ 25 levels, ≥ 2 % of a zone), ignores frame-wide changes over 60 % as lighting, and holds the gate open 3 s after the last motion. Zones are rectangles for now (`MotionZone`, whole frame by default); the zone editor task can switch them to polygons.
- 2026-11-10 — Daily summaries are computed on each camera (local time zone, once-a-second ticks of the current state and motion, bark detections ≥ 0.7) and uploaded every 15 min; the first upload after local midnight marks the previous day final, which sends the summary push once. Summaries are per camera, so a household with two cameras gets two summaries.
- 2026-11-10 — Training data is opt-in per household (owner toggle). Opting in only changes retention: clips with right/wrong feedback stay 90 days instead of 7, and the owner can export them via GET /training/labeled. No clip leaves the household's own bucket.
- 2026-11-10 — Plans: free = 1 camera, premium = the MVP limit of 4 (other limits unchanged for now). Premium is an App Store auto-renewable subscription (product ids in APP_STORE_PRODUCT_IDS) verified offline on the backend from the StoreKit 2 signed transaction (x5c chain pinned to Apple Root CA - G3, Apple's signing-cert OIDs, ES256). The app must set `appAccountToken` to the household id; one subscription unlocks one household. Cameras paired before a downgrade keep working; only new pairing is blocked. Limits are enforced only with ENFORCE_PLAN_LIMITS=true, so nobody loses cameras before the app can sell premium.
- 2026-11-10 — iOS Premium uses the native SubscriptionStoreView (iOS 17) with `appAccountToken` = household id; only the owner's phone observes StoreKit and reports transactions (purchase, `Transaction.updates`, `currentEntitlements` on launch and on Restore), and every screen reads the plan from `GET /subscription`. A transaction is finished only after the server accepts it (or answers `subscription_in_use`). The local `.storekit` file is for UI testing only: the backend rejects Xcode-signed transactions.
- 2026-11-10 — Live Activities are updated by APNs `liveactivity` pushes from the backend (no app wake needed). Content state is `{ state: DogState | null, online: Bool }` (no dates: ActivityKit decodes content-state with the default JSONDecoder). Per camera at most one update every 15 s (latest state wins, presence + state from one heartbeat are merged); priority 10 only for barking/whining/door/forbidden zone or going offline, to stay inside Apple's update budget. Rows older than 12 h (iOS's max activity lifetime) are dropped.
- 2026-11-10 — Design system: 4-pt spacing tokens, continuous radii 8/12/20, `.snappy`/`.smooth` motion (none under Reduce Motion). Glass (`.glassSurface()`, `GlassCard`, `StatusPill`) is only for chrome floating over media; content screens stay `List`/`Form`. Accent is a warm terracotta (#B4541F light, #E07B45 dark) chosen for contrast with white text; the app icon is a cream paw on that color with a dark variant, drawn by script (no third-party art).
- 2026-11-10 — Clip storage: Railway buckets supported alongside R2 (virtual-hosted URLs auto-detected for *.storageapi.dev, S3_FORCE_PATH_STYLE override, checksums only when required). Why: owner prefers keeping everything in Railway.
